Custom Code & Security

The process engine offers numerous extension points for customization of process behavior by using Java Code, Expression Language, Scripts and Templates. While these extension points allow for great flexibility in process implementation, they open up the possibility to perform malicious actions when in the wrong hands. It is therefore advisable to restrict access to API that allows custom code submission to trusted parties only. The following concepts exist that allow submitting custom code (via Java or REST API):

  • Deployment: Most of the custom logic is submitted with the deployment of a process, case, or decision model. For example, an execution listener invocation is defined in the BPMN 2.0 XML.
  • Queries: Queries offer the ability to include expressions for certain parameters (currently task queries only). This enables users to define reusable queries that can be repeatedly executed and dynamically adapted to changing circumstances. For example, a task query taskService.createTaskQuery().dueBeforeExpression(${now()}).list(); uses an expression to always return the tasks currently due. Camunda Tasklist makes use of this feature in the form of task filters.

Only trusted users should be authorized to interact with these endpoints. How access can be restricted is outlined in the next sections.

In addition, the process engine limits what custom code in process definitions can do:

  • The deny list for expressions and scripts blocks reflection and access to engine internals in expressions and JUEL scripts.
  • The optional allow list for task types and script languages restricts the built-in task types and the script languages that process definitions may use.
  • A customized expression manager also applies to JUEL scripts.

CIB seven in a Trusted Environment

When CIB seven is deployed in an environment where only trusted parties can access the system (for example due to firewall policies), no untrusted party can access the APIs for submitting custom code and the following suggestions need not be adhered to.

Deployments

Access to performing deployments can be restricted by using the authorization infrastructure and activating authentication checks for any endpoint a potentially untrusted party may access. The crucial permission for making deployments is Deployment/Create. Untrusted users should not be granted this permission.

Queries

Query access cannot be generally restricted with authorizations. Instead, a query’s result is reduced to entities a user is authorized to access. Thus, authorization permissions cannot be used to guard expression evaluation in queries.

The process engine configuration offers two flags to toggle expression evaluation in adhoc and stored queries. Adhoc queries are directly submitted queries. For example, taskService.createTaskQuery().list(); creates and executes an adhoc query. In contrast, a stored query is persisted along with a filter and executed when the filter is executed. Expressions in adhoc queries can be disabled by setting the configuration property enableExpressionsInAdhocQueries to false. Accordingly, the property enableExpressionsInStoredQueries disables expressions in stored queries. If an expression is used although expression evaluation is disabled, the process engine raises an exception before evaluating any expression, thereby preventing malicious code from being executed.

The following configuration combinations exist:

  • enableExpressionsInAdhocQueries=true, enableExpressionsInStoredQueries=true: Expression evaluation is enabled for any query. Use this setting if all users are trusted.
  • enableExpressionsInAdhocQueries=false, enableExpressionsInStoredQueries=true: Default Setting. Adhoc queries may not use expressions, however filters with expressions can be defined and executed. Access to filter creation can be restricted by the granting the authorization permission Filter/Create. Use this setting if all users authorized to create filters are trusted.
  • enableExpressionsInAdhocQueries=false, enableExpressionsInStoredQueries=false: Expressions are disabled for all queries. Use this setting if none of the above settings can be applied.

Task Filter Expression Whitelist

As of 2.0.14, 2.1.10 and 2.2.4, JUEL expressions in task filter criteria and ad-hoc task queries (e.g. assigneeExpression) are restricted to a whitelist by default. This closes the expression injection issue from Camunda Security Notice 157 for stored filters, ad-hoc task queries and or() branches.

Allowed by default (n = any non-negative number):

  • ${currentUser()}, ${currentUserGroups()}, ${now()}
  • ${dateTime()}, ${dateTime().withMillis(n)}, ${dateTime().withTimeAtStartOfDay()}
  • ${dateTime().withTimeAtStartOfDay().plusDays(n).minusSeconds(n)}
  • ${dateTime().plusDays(n)}, ${dateTime().plusDays(n).withTimeAtStartOfDay()}, ${dateTime().plusWeeks(n)}
  • plain literal values

All other expressions, e.g. ${dateTime().minusMonths(2)}, are rejected with HTTP 400. In the Tasklist, such a filter shows an error instead of the task list.

Finding Affected Filters

Before updating, find stored filters that use expressions:

SELECT ID_, NAME_, OWNER_, QUERY_ FROM ACT_RU_FILTER WHERE QUERY_ LIKE '%${%' OR QUERY_ LIKE '%#{%';

Also check custom TaskQuery code for *Expression values.

Allowing More Expressions

Set allowedFilterExpressions to a semicolon-separated list. It replaces the defaults, so include the defaults you still need. Numbers in brackets act as wildcards: ${dateTime().minusMonths()} also allows minusMonths(2).

  • CIB seven Run / Spring Boot: camunda.bpm.generic-properties.properties.allowedFilterExpressions
  • Tomcat (bpm-platform.xml) resolves ${…} as a placeholder; WildFly (standalone.xml) needs $${…}.

Switches

Property Default Effect
enableFilterExpressionWhitelist true (since 2.0.14 / 2.1.10 / 2.2.4) Whitelist on. false restores the old behavior (not recommended).
enableExpressionsInStoredQueries true false disables expressions in stored filters completely.
enableExpressionsInAdhocQueries false Expressions in ad-hoc task queries stay off; if enabled, the whitelist applies.

Deny List for Expressions and Scripts

Expressions and JUEL scripts are checked against a deny list, which is active by default. It applies to:

  • expressions in BPMN and CMMN models, for example camunda:expression, conditions and input/output mappings,
  • JUEL scripts (scriptFormat="juel"),
  • JUEL expressions in DMN decisions and the legacy JUEL-based FEEL engine (dmnFeelEnableLegacyBehavior),
  • EL functions used in these expressions.

Other script languages such as Groovy or JavaScript and the default FEEL engine are not restricted by the deny list. To restrict them, use the allow list for task types and script languages.

Default Entries

By default, the deny list blocks reflection and access to engine internals:

  • class and getClass
  • java.lang.Class, java.lang.ClassLoader, java.lang.reflect.AccessibleObject, java.lang.invoke.MethodHandle and java.lang.invoke.MethodHandles
  • the EL function lang:import
  • org.cibseven.bpm.engine.impl.cfg.ProcessEngineConfigurationImpl
  • java.lang.Runtime and java.lang.ProcessBuilder

In addition, the packages jakarta.el, javax.el and org.cibseven.bpm.impl.juel are always denied while the deny list is active. They cannot be removed.

An expression that uses a denied entry fails with an exception whose message names the matching deny list entry, for example getClass.

Configure the Deny List

The process engine configuration property deniedExpressionAccess adds entries to the defaults. Entries are separated by commas:

Entry Example Denies
Name getClass A property or method with this name. A property foo is also matched by getFoo and isFoo. Map keys are not checked by name.
Type or package java.lang.Runtime Access to objects of this type, including subtypes, nested types and, for a package, its subpackages. Results of method calls and EL functions are checked as well. A Class object counts as the type it represents.
EL function lang:import, :name The EL function with this prefix and name; :name is a function without prefix.
Member com.example.Admin#delete The property or method delete of the type com.example.Admin and its subtypes.
Removal -lang:import Removes a default entry. Only default entries can be removed.

Entries are matched in full. * is a wildcard, for example com.example.internal.* or delete*; an entry of wildcards only is rejected. An invalid entry fails the process engine configuration.

To allow a single default again, remove it. For example, getClass() needs -class,-getClass,-java.lang.Class.

The configuration is fixed when the process engine is built. EL functions are checked when an expression is parsed: a newly denied EL function also affects deployed process definitions once the deployment cache is rebuilt. Use the report mode to find these uses before you enforce the deny list.

Custom Expression Managers

The deny list is applied by the JuelExpressionManager and its subclasses, including the Spring and CDI expression managers. The process engine logs a warning if the configuration cannot be applied:

  • ENGINE-25011: the configured expression manager is not a JuelExpressionManager. The deny list does not apply to its expressions.
  • ENGINE-25012: a custom expression manager has its own expression access policy. deniedExpressionAccess and expressionHardeningMode are ignored.
  • ENGINE-25013: the expression manager was used before the process engine was built and keeps its previous policy. Build the process engine before you use the expression manager.

CIB seven 2.2.5 and 2.1.11

In CIB seven 2.2.5 and 2.1.11, the deny list is only active once deniedExpressionAccess has at least one entry. Any entry switches it on with the defaults plus the entries; to activate only the defaults, set an entry that changes nothing, for example java.lang.Runtime. In these versions, standalone DMN decisions, the legacy FEEL engine and JUEL scripts evaluated outside of a process engine command are not restricted. From CIB seven 3.0.0 on, the deny list is active by default.

Allow List for Task Types and Script Languages

The process engine configuration property executionAllowList restricts the built-in task types and the script languages that process definitions may use. Without configuration, nothing is restricted.

Set it to a comma-separated list of names, for example external, groovy. Once the list has entries, only the listed names are allowed:

  • the task types shell, mail and external (camunda:type) on service tasks, send tasks, business rule tasks, intermediate message throw events and message end events,
  • the script languages of scripts in BPMN and CMMN models, in process applications and in DMN decisions, for example groovy, javascript or juel.

Names are matched in full and ignore case. Script language aliases must be listed individually, for example js, ecmascript and graal.js in addition to javascript. Entries with a leading - or a * are rejected as a configuration error: to deny a task type or language, leave it out of the list. JUEL and FEEL expressions in DMN decisions are always allowed.

A use that is not allowed is handled as follows:

  • A new deployment that uses an unlisted task type is rejected.
  • A process definition that is already deployed fails when it reaches an activity with an unlisted task type.
  • A script in an unlisted language fails when it is executed.

The error has the code ENGINE-25003 and names the task type or script language and the activity, but not the configured list. External tasks that were created before the list was restricted can still be fetched and completed.

The hardening mode decides whether a violation is blocked or only logged.

Hardening Mode

The process engine configuration property expressionHardeningMode controls how a violation of the deny list and of the allow list is handled:

Value Effect
enforce (default) A violation is blocked.
report A violation is allowed and logged as a warning: ENGINE-25010 for the deny list, ENGINE-25004 for the allow list.
off Both checks are disabled.

The mode is fixed when the process engine is built.

Rollout: Report First, Then Enforce

To introduce a stricter deny list or an allow list without breaking running processes:

  1. Set expressionHardeningMode to report together with your deniedExpressionAccess and executionAllowList.
  2. Run your processes, decisions and cases, and check the log for ENGINE-25010 and ENGINE-25004.
  3. Adjust your models or the lists until no more warnings are logged.
  4. Set expressionHardeningMode to enforce, or remove the property.

Configuration Examples

CIB seven Run and Spring Boot (application.yaml, or default.yml / production.yml of CIB seven Run):

camunda.bpm.generic-properties.properties:
  deniedExpressionAccess: java.lang.System,com.example.Admin#delete
  executionAllowList: external, mail, groovy
  expressionHardeningMode: report

bpm-platform.xml or processes.xml:

<process-engine name="default">
  ...
  <properties>
    <property name="deniedExpressionAccess">java.lang.System,com.example.Admin#delete</property>
    <property name="executionAllowList">external, mail, groovy</property>
    <property name="expressionHardeningMode">report</property>
  </properties>
</process-engine>

Java:

ProcessEngineConfigurationImpl configuration = ...;
configuration
  .setDeniedExpressionAccess("java.lang.System,com.example.Admin#delete")
  .setExecutionAllowList("external, mail, groovy")
  .setExpressionHardeningMode("report");

Customized Expression Managers in JUEL Scripts

JUEL scripts (scriptFormat="juel" in script tasks, listeners, script conditions and input/output mappings) resolve names, properties and methods through the configured expression manager, like expressions in attributes do. Restrictions of a customized expression manager therefore apply to JUEL scripts as well.

This applies to a subclass of JuelExpressionManager and to a SpringExpressionManager with the beans property set. With the default expression managers, JUEL scripts are resolved by the script engine as before.

In JUEL scripts that use such an expression manager:

  • the restrictions of the expression manager apply, including to top-level names,
  • names that only the script resolver factories provide (configuration beans, Spring beans, mocks, a custom ResolverFactory) are not available,
  • context and lang:import are not available,
  • a process variable takes precedence over a bean with the same name,
  • unknown names fail with “Cannot resolve identifier”.

To resolve JUEL scripts through the script engine instead, override isAppliedToJuelScripts() in your expression manager to return false.
